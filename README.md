# rustgraph3d

A 3D map of a Cargo project at file level. Every `.rs` file in the workspace, plus the
source files of its dependency crates (from `~/.cargo/registry` and git checkouts), becomes
a sphere. Edges show which file reaches into which.

- Files are sized by line count and clustered by crate: workspace crates in the middle,
  dependencies on an outer shell.
- Click a file to see what it uses and what uses it, with the item names behind each
  edge (`Glob, Override`), its top-level items, and its module path.
- Narrow the view to 1, 2 or 3 hops around the selected file.
- Every file you visit is strung onto a numbered trail, drawn through the 3D scene.
- With `--serve`, the graph follows your jumps in Neovim, and "Open in Neovim" sends you
  back. Go-to-definition builds a chain of the types you jump through, from your code up
  through the crates it depends on, with a branch each time you go back and jump elsewhere.

## Install

```sh
cargo install --path .
```

## Use

```sh
rustgraph3d                       # current project, direct dependencies
rustgraph3d ~/src/my-worktree     # any project, workspace or git worktree
rustgraph3d --depth 0             # workspace only
rustgraph3d --depth 3 --prune     # deeper deps, but only files your code actually reaches
rustgraph3d -x windows-sys -x libc
rustgraph3d --serve 7878          # live viewer at http://127.0.0.1:7878/
```

It writes `rustgraph3d.html`, a single page you open in a browser. The page loads the 3D
engine from cdn.jsdelivr.net.

| Flag | Meaning |
| --- | --- |
| `-d, --depth N` | Dependency levels to include (0 = workspace, 1 = direct deps, default 1) |
| `--prune` | Drop dependency files the workspace never reaches |
| `-x, --exclude NAME` | Leave a crate out (repeatable) |
| `--dev` | Follow dev-dependencies of workspace members |
| `--all-targets` | Include examples, tests and benches |
| `-o, --output FILE` | Output page (default `rustgraph3d.html`) |
| `--json FILE` | Also write the raw graph |
| `--serve PORT` | Serve the page and accept editor events |
| `--nvim ADDR` | Neovim server address for "Open in Neovim" (needs `--serve`) |

## Neovim

`nvim/atlas.lua` connects Neovim and the viewer. It needs Neovim 0.10+ and `curl`.
From the repo root, symlink it into your config (or copy it there):

```sh
ln -s "$PWD/nvim/atlas.lua" ~/.config/nvim/plugin/atlas.lua
```

- `:Atlas` maps the project you are in, serves it, and opens the browser once the graph is
  built. `:AtlasStop` stops the server, which also stops when Neovim exits.
- `gd` in a Rust buffer (bound when a language server attaches) goes to the definition and
  adds the hop to the trail, labeled with the name it landed on. Keep jumping to follow a
  type up the dependency tree: `main.rs → struct Searcher (grep-searcher) → trait Sink → …`.
  Methods show as `Type::method`.
- Every other Rust buffer you enter is reported too, so `<C-o>` and `<C-i>` move you back
  and forth along the trail. A `gd` from an earlier step starts a new branch, and nothing
  is dropped: the branch button on a step switches between branches, and **Copy** puts the
  whole tree on the clipboard as indented text.
- **Open in Neovim** in the viewer sends you back to the file, at the definition line when
  you reached it with `gd`.

Options, set in `init.lua`:

```lua
vim.g.atlas_port = 7878                           -- default
vim.g.atlas_args = { "--depth", "3", "--prune" }  -- extra rustgraph3d flags
vim.g.atlas_gd = "gd"  -- false: keep your own gd and map <Plug>(atlas-definition) yourself
```

A definition outside the graph (std, or a crate beyond `--depth`) shows a notice instead of
a step: raise `--depth` to follow types further up. Pickers that jump on their own
(Telescope and the like) show up as plain visits, without the name.

Any editor can drive the trail:

- `GET /visit?file=<absolute path>&line=<n>` reports a visit.
- Adding `&from=<absolute path>&fline=<n>&sym=<name>` makes it a go-to-definition jump from
  `from` that landed on `sym`.

## How edges are found

`cargo metadata` gives the packages, their targets and dependency names. Each crate's
module tree is walked from its root file by following `mod foo;` (including `mod.rs`
layouts and `#[path]`). Every file is parsed with `syn`, and three kinds of edges are kept:

- **mod tree**: `mod foo;` from the parent file to the child file
- **use**: `use` declarations, resolved through `pub use` re-exports, glob re-exports,
  `pub extern crate` facades and `#[macro_export]` macros to the file that defines the item
- **paths**: qualified paths in code such as `super::b::run()` or `regex_syntax::hir::Hir`

Limits, since this reads source and does not type-check: method calls (`x.foo()`) are not
followed, `#[cfg]` is ignored (all module files are included, even other platforms'), and
code generated by macros or `build.rs` is not seen. Run with `RG3D_DEBUG=1` to list `use`
paths that did not resolve.
